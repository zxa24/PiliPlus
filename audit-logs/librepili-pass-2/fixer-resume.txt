## Review items (all done in the killed turn unless marked)
- **HEVC switch through `hevc_mp4toannexb` (P2):** at each configuration switch, the first sample now carries the new VPS/SPS/PPS in-band, and those sample entries become `hev1` (the type that allows in-band parameter sets). A single configuration stays `hvc1` with nothing added.
  - Verified with ffmpeg 8.1.2 on two x265 segments (640x360 then 320x240). Before the fix: 50 frames at 640x360 with `cu_qp_delta` errors. After: 25 frames at 640x360 plus 25 at 320x240, no errors. A switch back to the first configuration (A→B→A) also decodes correctly.
- **Re-download deleting the only copy (P2):**
  - A file that is only short (or missing) is resumed in place, which only appends.
  - A structurally damaged file is re-fetched into `<seg>.redl` and swapped in only once complete.
  - If segments are still damaged after that, the merge returns `damaged`. The entry is not marked complete, gets `failMerge`, and that is saved. The queue then waits, like a failed download, and restarting it fetches a fresh play URL.
- **Repair fighting the download slot (P2):** repairs use their own per-video slot (`_repairManagers`). Deleting the entry cancels it; starting another download no longer touches it.
- **Deleting an export wiping downloads in a shared folder (P2):** if the export's folder also holds download folders, only the export's own files are removed.
- **Moving an old export aside fails silently (P3):** the move now catches the error (e.g. a file open on Windows) and carries on. The deletion guards keep the export and the download apart.
- **OS clutter counted as "foreign" (P3):** dotfiles, `desktop.ini`, `Thumbs.db` and `ehthumbs.db` are ignored.
- **`checkSegment` gaps (P3):** in strict mode, any bytes after the last complete FLV tag count as damage, and a `RangeError` counts as damage. Tests cover a cut tag header and a cut 64-bit box header.
- **fd open failure leaves a black player (P3):** it now throws, so the player shows its error state. If `player.open` fails after the fd was opened, the fd is closed through a new `closeFd` channel method.
- **Picker result lost on activity recreation (P3):** the pending result, the I/O thread and a main-thread handler now live in the companion object. On a real finish the pending picker call is answered with null and the I/O thread shut down.
- **Persisted grants never used (P3):** removed `takePersistableUriPermission`, the 100-grant bookkeeping and the misleading comment.
- **Side-file cache (P3):**
  - Cache folders still shown by an open video page are kept, and released when that page closes (`LocalPlayer.release`). Folders no open page shows are removed on the next open.
  - Copies go through `.part` and a rename, so a failed copy never leaves a truncated file.
  - File names are sanitised: separators, `.` and `..` can't escape the cache folder. The `safeName` test was added this turn.
  - Listing comment images is wrapped in try/catch.
- **HEVC width/height 0 (P3):** the picture size is parsed from the SPS, including the conformance window. A test uses a real x265 SPS and gets 320x240.
- **`video/*` hiding MKV (P3):** the picker uses `*/*` with a MIME list (video/*, Matroska, FLV, octet-stream). The provider's MIME type is returned, and Dart rejects anything that is neither a known video extension nor `video/*`.
- **Two merges picking the same folder (P3):** the export folder is claimed before the first await, and released again if creating it fails.
- **Not changed, per instructions:** the heartbeat (stays off for all offline and local playback), the rejected `firstOrNull` item, and force-adding the new test files.

## Uncertainties
- **In-band parameter sets:** checked with software decode and ffmpeg's filter, not on MediaCodec itself. Only HEVC gets them. H.264 relies on `h264_mp4toannexb` handling the switch, which the auditor observed.
- **Resuming a short segment:** if the CDN ignores the Range header and the transfer then fails, `DownloadManager` rewrites the file from 0, and bytes that were there can be lost. That behaviour predates this work.
- **Closing the fd after `player.open` throws:** if mpv had already taken the fd before the throw, closing it could hit a reused descriptor number. I judge this unlikely.
- **Recommend feed:** the app request keeps its per-launch `buvid` header even when bound to the account; personalisation comes from `access_key`.
- **Cache folders:** one whose video page never opened stays until the next open or an app restart.
