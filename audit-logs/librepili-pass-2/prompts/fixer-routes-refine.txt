- [P2] [A] Joined HEVC with more than one sample entry plays corrupted when it goes through `hevc_mp4toannexb`, which is the Android MediaCodec path — lib/utils/flv_demux.dart:283-337, lib/utils/mp4_join.dart:42-75
  The box structure is correct. Each configuration becomes its own `hvcC` entry, and `stsc` uses the right index. FFmpeg signals the switch with AV_PKT_DATA_NEW_EXTRADATA. Probed with ffmpeg 8.1 on two x265 segments (640x360, then 320x240): software decode is correct. `-bsf:v hevc_mp4toannexb` ignores the new extradata, so segment 2 decodes with segment 1's VPS/SPS/PPS: "cu_qp_delta out of range" errors, and every frame comes out at 640x360. `h264_mp4toannexb` handles the switch correctly (320x240). The Android default hwdec is `mediacodec` (hwdec_type.dart:41), and **hypothesis**: the `hevc_mediacodec` decoder inserts that same filter, so in-app playback breaks after the switch. Fix: when the configuration changes, put the new VPS/SPS/PPS inline as length-prefixed NAL units in the first sample, or write `hev1`/`avc3`.
- [P2] [A] A segment re-download deletes the only copy before the replacement exists, and a failed merge still marks the entry complete — lib/services/download/download_service.dart:809-830, 780-803, 601-604
  `_redownloadSegment` calls `tryDel` on the segment, then downloads it from scratch. If that download fails (network error, expired durl, or cancelled by a start of another entry, see next item), `_repairSegments` throws. `_mergeDownload` then returns `output: null`, and `_completeDownload` still sets `isCompleted = true`. The result is a completed entry whose segment is missing or partial, with no export and no way to resume. Before this change, a slightly truncated FLV was joined leniently and played. Fix: download into `<seg>.redl` and swap it in only on success, or resume the existing file when it is only short. After the rounds run out, fall back to the lenient join, or leave the entry incomplete.
- [P2] [A] The repair download fights the normal download manager slot — lib/services/download/download_service.dart:809-830, 318-325
  The merge runs outside `_lock`, but `_redownloadSegment` writes the shared `_downloadManager` field. If the user starts another entry during the merge, `startDownload` cancels whichever manager is in the slot. Before the repair begins, that is the new download: the repair then overwrites the slot, and the new download is orphaned. Its `_onDone` reads the wrong manager's status, so the entry ends as pause rather than completed. After the repair begins, `startDownload` cancels the repair and the merge fails. Fix: keep the repair's DownloadManager in a separate field that deletion cancels.
- [P2] [A] Deleting the export still wipes downloads that live in a pre-guard shared folder — lib/services/download/download_service.dart:942-953 (with 271-302)
  The new code deliberately leaves `<root>/114514` alone when it already holds entry folders, and it protects the export from download deletion. The reverse direction is not protected. For the export entry, `_isOwnFolder("<root>/114514/114514.mp4")` is true, so `_deleteMerged` runs `Directory(<root>/114514).tryDel(recursive: true)`. That also deletes the `c_<cid>` download folders of av114514. Fix: in `_deleteMerged`, when the folder `_isOwnFolder` targets contains entry folders (entry file present), delete only the export's files.
- [P3] [A] Moving an old export aside fails silently when a file in it is open — lib/services/download/download_service.dart:273-302, 175, 244
  `page.rename(moved)` throws a FileSystemException on Windows if any file inside is open (for example, the export is playing). `_createDownload` is called without `await` or `try`, so the error is an unhandled async exception. The download is never created and the user gets no toast. Fix: wrap the move in try/catch and fall back to creating the page folder beside the export, or show an error.
- [P3] [A] `_isForeignFolder` treats OS clutter as "foreign" — lib/services/download/download_service.dart:1004-1005, 1096, 1121, 278
  Any top-level file counts, including `.DS_Store` (macOS Finder) or `desktop.ini`. Result: deleting downloads leaves the page folder behind. A later download of the same avid then finds a "foreign" folder with no entries and moves it aside as `"<avid> (视频)"`, creating a junk folder that looks like an export. Fix: ignore dotfiles and known OS files, or match only video extensions.
- [P3] [A] `checkSegment` misses some damage and can throw instead of returning false — lib/utils/flv_demux.dart:36-46; lib/utils/mp4_remux.dart:85-106; lib/utils/mp4_join.dart:140-149
  Probed. An FLV cut inside an 11-byte tag header returns `true`: the `while (pos + 11 <= length)` loop just exits. The durl size check covers this only when `bytes > 0`. An MP4 ending in a partial 16-byte header with size==1 throws RangeError (getUint64 on an 8-byte read), which escapes `checkSegment`, so the merge fails without any repair. Fix: in strict mode, treat leftover bytes after the last whole tag as damage, and catch RangeError as damage.
- [P3] [A] If the fd cannot be opened, the player still ends up "loaded" — lib/plugin/pl_player/controller.dart:806-816, 642-656
  When `openFd` returns null, `_createVideoController` shows a toast and returns. `setDataSource` then sets `dataStatus = loaded` and calls `_initializePlayer`, leaving a black player (or the previous media) instead of the error state. Fix: throw so that `dataStatus = error`. Minor related leak: if `player.open` throws after `openFd`, nothing closes the detached fd.
- [P3] [A] The picker's pending result can be lost, leaving the Dart future unresolved — MainActivity.kt:82-83, 116-122
  `AudioServiceActivity` reuses a cached FlutterEngine, so Dart state outlives the activity. If the activity is recreated while the picker is open (low memory or "don't keep activities"), `pendingPick` is null in the new instance. `onActivityResult` then returns silently, and `pickFile`/`pickFolder` never complete. Each activity instance also leaks its own `Executors.newSingleThreadExecutor()`. Fix: keep the pending result and executor in a companion or engine-scoped holder, and shut the executor down in `onDestroy`.
- [P3] [D] The persisted grants are never used — MainActivity.kt:138-162; lib/models_new/download/bili_download_entry_info.dart:47-54
  The comment says "Keeps read access across restarts (resume / reopen)", but `playUri` and `playKey` are "Not saved", and nothing reopens a URI later. Every pick still takes a persistent grant, up to 100, releasing the oldest one. Fix: drop `takePersistableUriPermission`, or actually save the URI for reopening.
- [P3] [A] Side-file cache is wiped on every open, and copies are not atomic — lib/services/local_player.dart:138-150; MainActivity.kt:226-240
  `_mirrorDir` recursively deletes `local_documents/`, including the side files of a video page still in the navigation stack (comment images load lazily). `copyDocuments` leaves a truncated file when a copy fails partway, which later parses as broken danmaku or comments. `DISPLAY_NAME` is joined into the path unchecked, so a `/` in the name creates subfolders. Also, `LocalDocuments.list` (local_player.dart:103) has no try/catch, so an error there silently aborts the folder open with no toast.
- [P3] [A] HEVC tracks are written with width/height 0 in `tkhd` and the sample entry — lib/utils/flv_demux.dart:240-252, 337-338
  FFmpeg takes the size from the SPS (probed: ffprobe reports 640x360). **Hypothesis**: players that trust the container size (Android MediaExtractor / gallery, QuickTime, browsers) may show 0x0 or refuse the exported file. Fix: parse the size from the SPS in `hvcC`, as `_avcDimensions` does for AVC.
