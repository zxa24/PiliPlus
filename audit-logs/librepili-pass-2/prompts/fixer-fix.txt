(reported by independent auditors; duplicates merged — satisfy all of them)

- [P1] [A] Restoring or resetting settings turns login mode off without re-reading the accounts, and a later Mine refresh permanently deletes the stored account — lib/utils/storage.dart:91-102

### Finding 7: download extras: request burst, overlapping exports, race with deletion, orphan folders
(reported by independent auditors; duplicates merged — satisfy all of them)

- [P2] [A] Download extras send a burst of comment requests per video, overlap across a batch, and recreate deleted folders — lib/services/download/download_extras.dart:143-225
  With the defaults (200 root comments, 10 replies each; download_settings.dart:40-55), each finished download makes about 10 MainList + up to 200 DetailList gRPC calls plus picture/emote downloads. These run `unawaited` (download_service.dart:586-596), so several exports overlap during batch downloads.
  If the user deletes a download while its export is still running, `CommentImages.save` (:489-495) recreates `<folder>/comments_images/`, leaving an orphan folder.
  **hypothesis:** the request volume triggers risk control (-352/-412), which would then also fail the next playurl requests.
  Fix: run exports one at a time from a queue, lower the defaults, and stop (without creating directories) once the entry has been deleted.

- [P3] [A] Download extras keep writing after the entry is deleted, and a crash mid-merge leaves an orphan partial folder — lib/services/download/download_extras.dart:480-501; lib/services/download/download_service.dart:585-594, 764-800

Fix: let deletion cancel the export (e.g. a cancelled flag checked between steps), and remove or reuse the half-written folder on retry.

- [P3] [A] Unawaited extras export races with deletion and recreates the exported folder — `lib/services/download/download_service.dart:586-596`; `lib/services/download/download_extras.dart:480-500`

### Finding 8: 416 without Content-Range truncates saved bytes; retry budget never resets on progress
(reported by independent auditors; duplicates merged — satisfy all of them)

- [P3] [A] DownloadManager: a 416 without a usable Content-Range empties a finished file — lib/services/download/download_manager.dart:121-133
  On 416 the code only treats the file as complete if `Content-Range` gives a total equal to what is on disk. If the header is missing or `total` does not parse, it runs `file.writeAsBytes([])` and starts over. Resuming always restarts at segment 0 (`_startSegment(…, 0, …)`), so every finished segment and every finished DASH stream is re-probed this way. **Hypothesis** (CDN behaviour): mirrors that send 416 without Content-Range force full re-downloads. Separately (lines 44-61), the 6-attempt retry budget never resets when a transfer makes progress, so a long download with occasional drops fails even though it keeps advancing.

- [P3] [A] A 416 without Content-Range truncates the saved file, and a later failure deletes it — `lib/services/download/download_manager.dart:121-133, 67-77`
  On resume of a file that is already complete, a CDN that answers 416 without a parseable `bytes */N` makes the code empty the file, even though all its bytes were saved. Multi-segment Type1 resume depends on exactly this 416 path for every finished segment. If the next attempts then fail (network down), `_fail` deletes the now-empty file. That contradicts the claim that saved bytes are never thrown away. Fix: on 416 with an unknown total, keep the file and use the size from `index.json`, or re-probe; never truncate a non-empty file there.

# How to work

Process the findings one at a time in the order listed. For each finding:

1. Print `=== Finding N: <short title> ===` to your output as a marker
2. Open the file at the finding's `<file>:<lines>` and read ~30 lines
   of surrounding context
3. If the fix depends on a library (vendored or imported), grep that
   library briefly to confirm API behaviour before relying on it. Don't
   read the whole library — just the relevant function
4. Make the minimal change. Don't refactor surrounding code, don't add
   tests, don't introduce new abstractions, don't fix neighbouring
   issues even if you see them
5. Print `--- Finding N: done ---` when that finding's edit is complete

**Order matters when findings cluster in the same file**: process them
in the codex-stated order (don't reorder), but if a later finding's
line numbers shift due to an earlier edit, locate that finding's code
by its **description** (what codex said is wrong), not by the original
line number.

# Constraints

- **Match existing style** — variable declarations, comment style,
  indentation. Look at neighbouring code, not abstract style guides
- **No new dependencies**
- **Single file per finding** unless the finding explicitly names
  multiple
- **NO git MUTATIONS at ANY phase — edit, self-test, AND auto-repair.**
  Specifically: no `git stash`, `checkout`, `reset`, `commit`, `rm`,
  `clean`, `restore`, or branch ops — *ever*, including while diagnosing a
  test failure. Diagnosis uses read-only `git show` / `git diff` / `git log`
  only. (A fixer once ran a `git stash` round-trip mid-diagnosis and
  re-applied an unrelated old stash → 22 files of merge-conflict cruft that
  blocked all commits.) You modify only the working-tree FILES the findings
  name; the orchestrator owns all git/commit operations.
- **Do NOT run tests during the per-finding edit phase** — that comes in
  the dedicated self-test step below; per-finding edits should only modify
  the working tree
- **Do NOT call the Agent tool** (it's excluded from your allowedTools
  anyway, but don't try). You're the only fixer in this pass

# Self-review before self-test (mandatory)

After applying ALL finding fixes but **before** running tests, do one
quick self-review pass. For each finding ask yourself two questions:

1. **Does my fix cover every case the finding's title and description
   imply, or only the literal example?** Codex often spots a bug class
   but cites one concrete instance. A literal-only fix scores
   `[PARTIAL]` on re-review and forces another round trip. Re-read the
   finding's description and enumerate cases mentally; if your edit
   only handles 1 of N, extend it in this same turn.

2. **Did my fix accidentally over-tighten behaviour the finding didn't
   ask for?** If the finding said "guard X with check Y" and you also
   changed unrelated behaviour Z, codex will flag `[OVER-ENG]`. Trim
   back to the minimum that addresses the finding's literal concern.

Spend at most ~30 seconds per finding on this. If both answers are
"clean", move on to self-test. If either flags a gap, refine in place
before testing — do not return to the orchestrator with a known-partial
fix. The orchestrator will not give you a second chance for free; iter
2 costs ~5 min and adds tokens. Iter 1 self-review pays for itself.

# Self-test after fixing (mandatory)

After applying ALL the finding fixes (but before producing your final
report), **run the project's tests yourself** to verify the fix didn't
break anything. Your self-test report is a **first-pass / advisory
signal**, NOT the commit gate — the orchestrator independently re-runs
the tests itself before commit, and THAT re-run is the authoritative
gate. Report honestly: a wrong self-test PASS is caught by the
orchestrator's re-run, so there's nothing to gain by overstating.

## Detect the test runner

- **`<command>`** (any non-empty string other than `auto-detect` or

- **`auto-detect`** (or empty / unset) — fall through to the

Search in this order (first hit wins):

1. `package.json` with `scripts.test` → `npm test` (or `pnpm test` /

2. a repo-local test entry script such as `tests/run_nonhost_checks.js` →

3. `pytest.ini` / `pyproject.toml [tool.pytest]` / `tox.ini` with

4. `Cargo.toml` → `cargo test --no-fail-fast`
5. `Makefile` with a `test:` target → `make test`
6. `go.mod` → `go test ./...`
7. Plain `tests/test_*.js` ad-hoc Node scripts → run each via `node`

8. Nothing detected → emit `TEST RUNNER: none-detected` in the report
   block

If multiple runners apply (e.g. both npm test AND ad-hoc node tests),
run all of them and aggregate results.

## Auto-repair test infrastructure (no-ask)

If running the detected test command fails because **the test infra
itself is broken** (not because the audit broke a behaviour), repair
the infra automatically and re-run. Do NOT ask. Surface the repairs
done in the `INFRA REPAIRS` line of the final report block.

INFRA-level patterns (auto-repair without asking):

- **Missing dependencies**: `npm install --ignore-scripts` /
  `pip install --only-binary=:all: -r requirements.txt` /
  `cargo fetch` / Playwright browser binaries (`npx playwright install`)
  missing → run the install. If install itself fails, surface that.
  These flags block the script-execution path that
  `dangerously-skip-permissions` + Bash would otherwise expose: npm's
  `--ignore-scripts` skips lifecycle hooks; pip's `--only-binary=:all:`
  refuses to build from source distributions, eliminating the
  `setup.py` execution path; cargo `fetch` doesn't run scripts;
  `npx playwright install` is a single-binary download. If a project's
  test deps require source builds (e.g. compiled extensions without
  prebuilt wheels) or a project genuinely needs lifecycle scripts to
  test, the install will fail — surface that to the user as a
  route-choice rather than silently relaxing the constraint.
- **Broken paths in test scripts**: hardcoded paths to legacy
  directories (e.g. `tests/translator_app/app.js` when `app.js`
  moved to root) → fix the path references in the test scripts.
- **Stale test config**: `playwright.config.js`, `pytest.ini`,
  `package.json scripts.lint` pointing at non-existent files →
  update the config.
- **Missing test helper imports**: helpers moved/renamed since tests
  were written → align imports.
- **Test selectors too loose for new UI**: Playwright spec uses
  `label.btn.primary` and a recent commit added a 2nd matching
  element → tighten the selector (`:has-text(...)` or `#id`).
- **Permission issues on test artifact dirs**: tests can't write to
  `tests/screenshots/` etc. → `mkdir -p` and re-run.

REAL behavioural failures (do NOT auto-repair, just report):

- Assertion failures: `expect(x).toBe(y)` failed with x !== y
- Behaviour deltas: feature flag now off, UI element absent, output
  format different from expected
- Anything where the test code itself is correct and ran successfully,
  but the assertion conclusion was negative

Auto-repair loop limit: up to 3 cycles per test runner. If a runner's
tests still fail with INFRA errors after 3 repair attempts, stop
repairing it and report the remaining failures as `INFRA-PERSISTENT`.

# What to report back

Return ALL of, in this order:

1. **Per-finding summary** — for each finding, 1-2 sentences on what
   you changed
2. **`git diff` output** — run `git diff` (no path arg) and include
   the full cumulative diff for the audit's fixes (NOT the test infra
   repairs, which go in the TEST RESULTS block instead). Codex's
   re-review will see this exact diff so it must be accurate
3. **Uncertainty list** — for each finding, anything you weren't sure
   about (API behaviour, semantic edge cases, whether your fix
   tightens behaviour beyond the finding's literal ask)
4. **TEST RESULTS block** — exactly this format so the orchestrator
   can parse it deterministically:

```
TEST RESULTS:
  runner: <npm test | pytest | cargo test | node tests/X.js | none-detected>
  command: <exact command line invoked>
  exit_code: <0 | non-zero>
  total: <N>
  passed: <N>
  failed: <N>
  skipped: <N>
  duration_ms: <approx>

INFRA REPAIRS (during auto-repair, empty if none):
  - <file>: <one-line description of what was changed>
  - <file>: ...

REAL FAILURES (audit-fix-caused regressions, empty if none):
  - <spec name + line>: <one-line failure summary>
  - <spec name + line>: ...

INFRA-PERSISTENT (failures that hit the 3-cycle repair cap, empty if none):
  - <runner / file>: <reason still failing>

OVERALL: <PASS | INFRA-ONLY-FAIL | INFRA-PERSISTENT | REAL-FAIL | NO-RUNNER>
```

`OVERALL` semantics:
- `PASS`: all tests pass (or skipped) and no failures of any kind
- `INFRA-ONLY-FAIL`: some tests failed for INFRA reasons but
  auto-repair fixed them and a subsequent re-run passed; audit fix
  is not regressed
- `INFRA-PERSISTENT`: some tests failed with infra errors that
  survived the 3-cycle auto-repair cap; the runner exists but
  couldn't be made to run reliably. Orchestrator treats this as
  STOP (unverified state — more concerning than NO-RUNNER because
  the test infra exists but can't be trusted)
- `REAL-FAIL`: at least one entry in REAL FAILURES — audit fix
  probably broke behaviour; orchestrator should STOP
- `NO-RUNNER`: no test runner detected; can't verify automatically
