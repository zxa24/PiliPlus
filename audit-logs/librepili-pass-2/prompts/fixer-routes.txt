## R2 (pass2-D2) — make multi-segment merges not fail
Finding (pass 2): when Type1 (durl) segments cannot be joined/remuxed, they are kept as separate parts and in-app playback plays only part 1. The user rejected both "play all parts" and "just warn": they want the merge itself to succeed. Eliminate the fallback causes as far as possible:
- MP4 segments whose `stsd` (codec config) differ: MP4 allows several sample entries per track — join by emitting all distinct sample entries in stsd and pointing each chunk's stsc sample_description_index at the right one, instead of throwing UnsupportedError.
- FLV: codec config (AVC sequence header / AudioSpecificConfig) that changes mid-stream or between segments → same multi-sample-entry approach. Also support HEVC in FLV if Bilibili can deliver it (check both the legacy codec id 12 convention and Enhanced-RTMP FourCC 'hvc1'); if you conclude it cannot occur for bilibili durl, say why.
- Corrupt/truncated segment (FormatException while reading): treat as a download problem — re-download that segment (bounded retries) and retry the merge — instead of falling back.
- Keep the separate-parts fallback only for genuinely impossible cases (e.g. a codec with no MP4 mapping), and list exactly which cases remain.
Add unit tests on synthetic data for each newly-handled case (different stsd across segments; config change mid-FLV).
