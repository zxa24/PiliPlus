## 3. Uncertainty list

- **Finding 31 — no change made, premise disproved.** I measured it: with `RetryInterceptor(dio, 2, 1)` and an always-failing adapter, an interceptor registered *after* it sees the error **exactly once** (adapter called 3×, `onError seen=1`). The innermost recursion level already calls `handler.next(err)`, which is what reaches `AccountManager.onError` — so `toast(err)` and `_saveCookies` *do* run. Switching the outer `handler.reject` → `handler.next` raised it to **3** (one toast/`_saveCookies` per retry level). dio 5.11.1 confirms it: `errorInterceptorWrapper` `throw`s on `reject` and continues on `next`. Left as-is; the probe test was deleted.
- **Finding 37 — reverted after implementing it.** I wrote the coalescing, then found `ReplyController.queryBySortType()` and `PageOrderMixin.updatePageOrder()` mutate a parameter and then call `onReload()`. Sharing an in-flight refresh would serve data fetched with the *old* sort/order while the UI already shows the new one. The finding itself calls the current behaviour "Correct" and conditions the fix on "if traffic matters", so I chose correctness. A safe version would need per-parameter keying, which is beyond "smallest change" — flagging for your call.
- **Finding 35 (geetest) — unverified.** I made the one-line change as asked but **cannot verify the captcha still loads**: that needs a real login attempt on a device. If geetest serves any asset over plain http, this will break login. Easy to revert.
- **Finding 26 (gradle) — deliberately narrower than the literal ask.** I did *not* make the release variant fail outright when no signing config exists; that would break `flutter build apk --release` for any contributor without `key.properties`. Instead the CI guard now requires all four secrets, and gradle fails when `key.properties` is half-configured. If you want the hard CI-only failure too, say so.
- **Finding 3** — excluding credentials from the snapshot means an undo of an import that *replaced* the WebDAV password restores the pre-import settings but keeps the **imported** password. That is exactly the "restoring them from the live box" semantics the auditor proposed, but it is a small fidelity loss in that one case.
- **Finding 18** — `csrf` now returns `''` instead of throwing when `bili_jct` is gone. Logging out an already-expired account server-side (`LoginHttp.logout`) will now send an empty csrf and fail cleanly rather than throwing; the account is still removed locally.
- **Finding 2** — `launchURL` uses a denylist, not the literal http/https allowlist, because `webview/view.dart:146,160` deliberately hands custom app schemes (`weixin://`, `bilibili://`…) to the OS; an allowlist would break that. `_toWebview` and the WebView itself *do* use a strict http(s) allowlist.
- **Finding 22** — the authority check is provably correct; I did not try to verify the auditor's own hypothesis about AOSP's same-uid grant fast path (they noted the hole doesn't depend on it).
- **Finding 27** — `pubspec.lock` is now regenerated; CI's `flutter pub get` will produce the same file.
- **Finding 20** — one behaviour change beyond pure guarding: `bilibili://video/123?cid=abc` used to throw, now falls through to the `videoPush` (no-cid) branch instead of doing nothing.
