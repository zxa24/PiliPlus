## Uncertainties

- **A2, no context:** `launchURL` needs a `BuildContext` for the confirm, and takes `Get.context`. If that is null (very early startup, or a call from outside the widget tree) a non-http(s) url is now silently dropped rather than opened. All call sites I checked are user-initiated from a live page, so this should not fire, but it is a behaviour change if it does.
- **A2, our own scheme:** an unrecognised `bilibili://` link inside a web page (one `PiliScheme.routePush` did not match) now prompts before being handed back to the OS. I judged that correct rather than exempting `bilibili`; say if you'd rather it be silent.
- **A12, Linux:** I could not run Linux. The claim that the anonymous jar is reinstated there rests on reading `WebviewPage.openLinux` (`webview/view.dart:67-78`) — it builds the injection JS from `AnonymousAccount()` for every non-account window. If a future change opens a Linux webview without going through `openLinux`, that window would have an empty jar.
- **A30, prefix semantics:** with the default `https://www.bsbsb.top` (no path) the prefix is empty, so every path on that host still matches — same as before, and correct for the default. The narrowing only takes effect when a user sets a server *with* a path. I did not add a port to the reserved-host check; `https://api.bilibili.com:8443/sb` is refused on the host alone.
- **A30, existing bad values:** a `blockServer` already saved that the new rule rejects now makes `_isBlockServer` false — SponsorBlock requests to it would carry cookies rather than none. The dialog will refuse to save it again. Arguably it should be reset to the default on load; I left it, since silently rewriting a user setting is worse.
- **A31:** the `finish()` split relies on `extra['_rt']` being absent on the caller's own attempt and present on every nested one. That holds because `RequestOptions` is shared across retries. If some other interceptor were to copy or clear `extra`, the outermost attempt could be misclassified and the error would be rejected instead of forwarded. Not the case today.
- **A37, residual risk:** coalescing is now safe for every parameter-changing path I found, but the guarantee is a call-site convention, not a type-level one — a future controller that mutates request state and calls `onRefresh()` directly without `markRefreshStale()` would attach to a stale refresh. The doc comment on `markRefreshStale` says so. A stricter design would thread the parameters through `queryData`, which is a much larger refactor.
- **A37, error propagation:** a second caller that attaches now also sees the first request's error. Previously it would have issued its own request and seen its own error. Same class of failure, different instance.
