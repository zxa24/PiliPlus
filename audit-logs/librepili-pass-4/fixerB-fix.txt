## 3. Uncertainty list

- **F2** — `_exportFilePath` can also throw `FileSystemException` (e.g. the export folder cannot be created). That now yields `failMerge` + retryable rather than "complete with no file"; I believe that is the better outcome but it is slightly wider than the literal "missing input" case.
- **F6** — reachability was flagged hypothesis by codex and I did not re-verify it; the null-collapse itself I re-confirmed in `path-1.9.1/lib/src/context.dart:264-283`. The `'0'` fallback folder name is invented — a foreign `entry.json` with no `type_tag` will now download into a *new* `0/` folder rather than adopting whatever layout that tool used.
- **F8** — `onReceiveProgress` now also fires at the resume offset. Only `_onReceive` consumes it and it handles that fine, but it is a behaviour change for any future consumer.
- **F9** — `_pickTree` keeps its phantom `mergedPath`: the mirrored side files are named `<video-base>.*` and consumers derive dir+base from `mergedPath`, so nulling it there would break the comments/subtitle lookup. I only nulled the case the finding names (nothing mirrored).
- **F11** — I made this a hard `FormatException` in `checkImport` rather than a soft warning, because that is the one place the finding pointed at and it runs *before* anything is cleared. Trade-off: one duplicated follow now blocks the whole restore. Say the word and I'll downgrade it to a toast + proceed.
- **F14** — this moves `tmpDirPath` on mobile (`<tmp>/` → `<tmp>/LibrePili/`). I checked every `tmpDirPath` consumer and found no FileProvider XML in the repo, but I could not exercise an actual Android share/save-to-gallery. Also, `loadApplicationCache` still sums the whole temp dir, so the displayed cache size will now exceed what clearing frees; fixing that was outside the finding.
- **F16** — **I made no behavioural change and this is deliberate.** The suggested fix is unsound here: `_write` copies each chunk as one contiguous `setPosition`+read of `c.length` bytes, and `stsc`/`stco` address samples as chunk-offset + cumulative size, so a multi-sample chunk *must* be contiguous in the source. FLV samples are tag payloads separated by the 4-byte PrevTagSize + 11-byte tag header + codec header, and interleaved with the other track — never contiguous. Grouping them would write tag headers into `mdat` and corrupt the sample tables. (The fragmented-MP4 path can group because `dataOffset += size` makes its samples contiguous by construction.) The `onProgress` half of the cost is already nil: no caller passes `onProgress`. A real fix would need buffered sequential reading in `_write`, which is a refactor of shared code.
- **F18** — the resume check compares against `entry.totalBytes`, which is the *video* stream's size (the audio manager reports no progress); the audio stream therefore gets no size check. A fresh entry has `totalBytes == 0`, so the check is inert on first download. I assumed CDN mirrors of one stream report identical lengths.
