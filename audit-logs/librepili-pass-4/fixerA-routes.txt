**iOS** (`ios/Runner/Info.plist`): `CFBundleURLTypes` is now just the `bilibili` entry. Removed the dict claiming `http`/`https` as app URL schemes, and with it the nested `CFBundleURLTypes` → `CFBundleURLSchemes` array of bilibili.com *hostnames* (not schemes; iOS ignores a nested `CFBundleURLTypes` entirely — hostname matching is what Universal Links are for). `LSApplicationQueriesSchemes` still lists `https`/`http`; that is the unrelated `canOpenURL` allow-list and I left it.

**macOS** (`macos/Runner/Info.plist` + `macos/Runner/AppDelegate.swift`): added `CFBundleURLTypes` for `bilibili`, `CFBundleDocumentTypes` for the nine extensions, and `UTImportedTypeDeclarations` for `org.matroska.mkv` / `org.webmproject.webm` / `com.adobe.flash.video` (the three macOS does not declare itself), so the extension list is backed by real UTIs.

**The bridge the brief asked me to check for: half of it was missing, so I added it.** By reading:
- `bilibili://` needs **no** new native code. `AppLinksMacosPlugin.handleWillFinishLaunching` installs an `NSAppleEventManager` handler for `kAEGetURL` and pushes the url into the same stream `PiliScheme.init()` already listens to (`stringLinkStream` → `_desktopRoutePush` on desktop). The plist declaration was the only missing piece.
- "Open with" **did** need one. Finder sends a document as a `file:` URL to `application:openURLs:`; `FlutterAppDelegate.mm:68` only offers those to plugins implementing `handleOpenURLs:`, and `AppLinksMacosPlugin` implements no such method (it only has `handleWillFinishLaunching`) — so the URL would have been dropped and the app would have appeared in "Open with" and then done nothing. I overrode `application(_:open:)` in `AppDelegate.swift`: file URLs go to `AppLinks.shared.handleLink(link:)`, everything else to `super`.
- That lands exactly where the Dart side already expects it: `PiliScheme._localFile` accepts a `file:` URI (`Uri.tryParse(link)?.toFilePath()`, which also decodes `%20`), checks it exists, and `_openFile` → `windowManager.show()/focus()` → `LocalPlayer.open()` — the same path Linux takes. Cold start works because the native plugin stores the first link as `initialLink` and `onListen` replays it to the first subscriber.
- The nine extensions match `LocalPlayer.videoExtensions` (`local_player.dart:20-30`) exactly, and the Linux `.desktop` `MimeType=` list one-for-one.
- Sandbox: both `macos/Runner/*.entitlements` already carry `com.apple.security.files.user-selected.read-write`, which covers a Finder-opened document. No entitlement change needed.
- `import app_links` from the Runner target is valid: `macos/Flutter/GeneratedPluginRegistrant.swift:8` already does exactly that, and the Podfile uses `use_frameworks!`.

## Uncertainty list

- **Nothing on iOS/macOS was built or run** — there is no Mac here. What I verified is by reading: both plists parse cleanly under `plistlib` (I ran that), `FlutterAppDelegate.mm:68` forwards `application:openURLs:` only via `handleOpenURLs:`, `AppLinksMacosPlugin` has no `handleOpenURLs:`, `AppLinks.shared` / `handleLink(link:)` are `public`, and `GeneratedPluginRegistrant.swift` already imports the module. **Unverified by execution:** that `application(_:open:)` is the callback Finder actually reaches for `CFBundleDocumentTypes` opens on the deployment target, and that the Swift override compiles against `FlutterAppDelegate`'s Objective-C `application:openURLs:` signature. Both are standard, but a macOS CI run is the real gate.
- **Possible double delivery of `bilibili://`.** app_links claims `kAEGetURL` with its own handler, which should pre-empt AppKit's default translation into `application:openURLs:`. If some macOS version delivers both, a `bilibili://` link would arrive twice. My override only takes `isFileURL` URLs and passes the rest to `super`, so it does not *add* a duplicate — but I could not test the interaction.
- **`Package: LibrePili` in the Debian control is not a valid Debian package name** (policy requires lowercase). That is pre-existing, outside what R1 asked, and changing it to `librepili` would change the installed package identity and break the upgrade path for anyone who already installed it. Flagging rather than changing — your call.
- **`LSHandlerRank: Alternate`** means LibrePili offers itself in "Open with" without trying to become the default handler for these types. If you'd rather it compete for default, that becomes `Default` or `Owner`.
- **`.ts` is ambiguous**: `public.mpeg-2-transport-stream` is right for video, but `.ts` is also TypeScript. With `Alternate` rank this only adds LibrePili to the "Open with" menu for `.ts` files; it will not steal them from an editor.
- The macOS `CFBundleURLTypes` addition only takes effect after LaunchServices re-registers the bundle (normal on install/first run; during development it can need `lsregister -f`).
