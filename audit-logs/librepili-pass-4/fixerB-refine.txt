## B16 — measured, then optimized

I was wrong in iter 1: I argued from the code that grouping was impossible and skipped the measurement. The measurement says the cost is real and the grouping *is* possible — a chunk must be contiguous in the **output** file (`stco` names one offset for it), not in its source, so an FLV chunk can list its samples' source ranges one by one.

Probe: synthetic 10-minute FLV, 41 087 samples (15 000 video @25 fps + 26 087 AAC), realistic sizes (2 kB P-frames, 15 kB key frames every 2 s, 350 B audio) = 41.8 MiB. Median of 3 runs after a warm-up pass.

| | before | after buffering | after buffering + grouping |
|---|---|---|---|
| `remuxFlv` wall time | **49 570 ms** | 217 ms | **185 ms** (≈268× faster) |
| chunks | 41 087 | 41 087 | **1 193** (600 video + 593 audio) |
| `stco` | 164 380 B | 164 380 B | **4 804 B** (34× smaller) |
| `moov` total | 351 819 B | 351 819 B | **192 255 B** (−45%) |

Two changes, both in the shared writer so the DASH path benefits too:

1. **Buffered I/O** (`mp4_remux.dart` `_write`) — this is where the 49.6 s lived. Output accumulates in a 4 MiB buffer (same allocation as the old read buffer); each source gets a 1 MiB sliding `_ReadWindow`. Chunks run forward through a source, so ~all per-sample reads are served from memory: 41 087 `setPosition`+`readInto`+`writeFrom` triples → ~90 syscalls. Ranges larger than the window still stream straight through.
2. **Chunk grouping** (`flv_demux.dart`) — samples accumulate into ~1 s chunks (same `_maxChunkSeconds` as the fragmented-MP4 path), breaking on a sample-description or source-file change. `_Chunk.ranges` holds the per-sample source ranges. This is what cuts `stco`/`moov`; it costs no wall time.

Peak memory is 4 MiB + 1 MiB per source (5–6 MiB) vs. 4 MiB before.

Verified at scale, not just in unit tests: the 10-minute output reads back as 15 000 video samples / 33 975 000 B and 26 087 audio / 9 130 450 B — every sample, byte counts exact — and `checkSegment` passes.

## B17 — real join test in `test/utils/flv_demux_test.dart`

Codex named that file as the home, so the join coverage went there (the separate `mp4_join_test.dart` I added in iter 1 duplicated 158 lines of helpers; I folded its unique assertion in and deleted it). Two new tests in the `joinMp4` group:

- **`joined segments: every sample lies where its table says`** — joins two synthetic segments, then walks the *sample table of the output* for both tracks: for each chunk it takes the `stco` offset and adds up the `stsz` sizes, and asserts the bytes at that position equal the exact payload that segment wrote. That covers sample count (per track and summed across chunks), sizes, and that both segments' payload bytes survive — plus `durations`, `ctos` and `syncs` for all six samples. Two debug fields (`sampleCounts`, `chunkOffsets`) were added to the existing test-only summary to make this possible.
- **`segments whose track sets differ are not joined`** — video-only segment joined onto video+audio → `UnsupportedError`. The codec-mismatch refusal (`a different codec is still not joined`) and the differing-configuration path (two sample entries, *not* refused) were already covered.

I mutation-tested the placement walk (reversed the range order inside a chunk): it fails with `bytes of sample 0 (t0)`, so it is a real test, not a tautology.

Three pre-existing assertions changed meaning because chunk granularity changed — `descIndexes` `[1,1,2,1]`→`[1,2,1]` etc. I updated them and added `sampleCounts` alongside each, which pins the sample→description mapping more tightly than the old per-sample chunk list did.
